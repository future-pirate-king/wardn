# SOPS

[SOPS](https://github.com/getsops/sops) (Secrets OPerationS) encrypts the values in YAML/JSON files while keeping keys and structure readable. Wardn decrypts SOPS-encrypted manifests at apply time, so plaintext secrets never exist in Git.

## Supported Key Providers

| Provider | Status |
|----------|--------|
| AWS KMS | ✅ Supported |
| Google Cloud KMS | ✅ Supported |
| age | ✅ Supported |
| HashiCorp Vault Transit | ✅ Supported |
| PGP | ✅ Supported |

## How It Works

```
┌─────────────┐  encrypted  ┌──────────┐  decrypt   ┌──────────────┐
│  Developer  │────────────▶│   Git    │───────────▶│   Operator   │
│  (sops -e)  │             │  Repo    │  at apply  │  (KMS key)   │
└─────────────┘             └──────────┘            └──────┬───────┘
                                                           │
                                                           ▼
                                                   ┌──────────────┐
                                                   │  K8s Secret  │
                                                   │  (plaintext) │
                                                   └──────────────┘
```

1. **Developer** encrypts the secret file with `sops -e` using a KMS key
2. **Git** stores only the encrypted values
3. **Operator** fetches the file, decrypts it with the KMS key at apply time
4. **Cluster** receives the plaintext Secret

## Tutorial: Encrypt a Secret with AWS KMS

<Steps>

### Step 1: Create a KMS Key

```sh
aws kms create-key --description "Wardn SOPS key"
aws kms create-alias --alias-name alias/wardn-sops --target-key-id <key-id>
```

Grant the operator's IAM role access to this key.

### Step 2: Create a Plaintext Secret

```yaml
# secret.yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
stringData:
  username: admin
  password: super-secret-password
```

### Step 3: Encrypt It

```sh
sops --encrypt \
  --kms arn:aws:kms:us-east-1:123456789:key/abcd-1234 \
  --in-place secret.yaml
```

The file now looks like:

```yaml
apiVersion: v1
kind: Secret
metadata:
    name: db-credentials
stringData:
    username: ENC[AES256_GCM,data:K8sJ...,iv:...,tag:...,type:str]
    password: ENC[AES256_GCM,data:x9Pq...,iv:...,tag:...,type:str]
sops:
    kms:
        - arn: arn:aws:kms:us-east-1:123456789:key/abcd-1234
          created_at: "2024-01-15T10:30:00Z"
          enc: AQICAHh...
```

### Step 4: Commit to Git

```sh
git add secret.yaml
git commit -m "Add encrypted db credentials"
git push
```

### Step 5: Configure the Secret Store in Wardn

In the Wardn UI:

1. Go to **Settings → Secret Stores**
2. Click **Add Store**
3. Select **SOPS** as the type
4. Choose **AWS KMS** as the key provider
5. Enter the KMS key ARN
6. Provide AWS credentials (or use IRSA/workload identity)
7. Click **Test Connection**

### Step 6: Reference in Your GitApplication

```yaml
apiVersion: cd.wardn.space/v1alpha1
kind: GitApplication
metadata:
  name: my-app
spec:
  repoURL: https://github.com/myorg/my-app
  path: manifests
  # SOPS files in the path are automatically detected and decrypted
  syncPolicy:
    automated: true
```

Wardn automatically detects `.sops.yaml`-encrypted files in the manifest path and decrypts them before applying.

</Steps>

## Using .sops.yaml for Team Workflows

Create a `.sops.yaml` at the repo root to configure encryption rules:

```yaml
creation_rules:
  # Production manifests use the production KMS key
  - path_regex: manifests/production/.*\.yaml
    kms: arn:aws:kms:us-east-1:123456789:key/prod-key

  # Staging uses the staging key
  - path_regex: manifests/staging/.*\.yaml
    kms: arn:aws:kms:us-east-1:123456789:key/staging-key

  # Default
  - kms: arn:aws:kms:us-east-1:123456789:key/default-key
```

Now `sops -e --in-place manifests/production/secret.yaml` automatically picks the right key.

## Using age for Local Development

For local development without cloud KMS:

```sh
# Generate an age key
age-keygen -o key.txt

# Encrypt with age
sops --encrypt --age age1abc... --in-place secret.yaml
```

Store the private key as a Kubernetes Secret for the operator:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: sops-age-key
  namespace: wardn-system
stringData:
  key.txt: |
    # created: 2024-01-15T10:00:00Z
    # public key: age1abc...
    AGE-SECRET-KEY-1XYZ...
```

## Troubleshooting

### Decryption Fails

```sh
# Check operator logs
kubectl logs -n wardn-system deployment/wardn-operator | grep -i sops
```

Common causes:
- **KMS access denied** — the operator's IAM role lacks `kms:Decrypt` permission
- **Wrong key ARN** — the secret was encrypted with a different key
- **Missing credentials** — AWS credentials not configured for the operator

### Secret Values Appear as ENC[...] in the Cluster

The file wasn't decrypted before apply. Verify:
1. The file is actually SOPS-encrypted (has a `sops:` section)
2. A SOPS secret store is configured and connected
3. The operator version supports SOPS decryption

## Security Notes

- **Rotate keys** — periodically rotate KMS keys and re-encrypt secrets
- **Scope IAM policies** — the operator should only decrypt keys it needs
- **Audit** — KMS CloudTrail logs show every decryption operation
- **Never commit** `.sops.yaml` private keys or age key files
