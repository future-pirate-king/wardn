# Vault Direct

<Callout type="info">
  Direct Vault integration is planned for a future release. This page describes the target design.
</Callout>

Vault Direct lets Wardn fetch secrets from HashiCorp Vault at apply time — without SOPS encryption or the External Secrets Operator. Your Git manifests reference Vault paths, and Wardn resolves them during sync.

## How It Works

```
┌──────────┐   reference   ┌──────────┐   fetch    ┌────────┐
│   Git    │──────────────▶│ Operator │───────────▶│ Vault  │
│ (paths)  │               │          │  at apply  │        │
└──────────┘               └────┬─────┘            └────────┘
                                │
                                ▼
                         ┌──────────────┐
                         │  K8s Secret  │
                         │  (resolved)  │
                         └──────────────┘
```

## Planned Configuration

### 1. Register a Vault Secret Store

Via the UI (**Settings → Secret Stores**) or API:

```json
{
  "name": "production-vault",
  "type": "vault",
  "config": {
    "address": "https://vault.example.com:8200",
    "authMethod": "kubernetes",
    "kubernetesRole": "wardn-operator",
    "mountPath": "secret"
  }
}
```

### 2. Reference Vault Paths in Manifests

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
  annotations:
    wardn.io/vault-path: secret/data/prod/my-app/db
stringData:
  username: "{{ vault:username }}"
  password: "{{ vault:password }}"
```

Wardn fetches `secret/data/prod/my-app/db` from Vault and substitutes the values at apply time.

### 3. Or Use a Declarative Reference

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
type: Opaque
x-wardn-vault:
  path: secret/data/prod/my-app/db
  keys:
    username: username
    password: password
```

## Authentication Methods

| Method | Use Case |
|--------|----------|
| Kubernetes auth | Operator running in-cluster (recommended) |
| AppRole | Operator running outside the cluster |
| Token | Simple setups, short-lived tokens |

### Kubernetes Auth (Recommended)

```yaml
config:
  address: https://vault.example.com:8200
  authMethod: kubernetes
  kubernetesRole: wardn-operator
```

Vault policy for the operator:

```hcl
path "secret/data/prod/*" {
  capabilities = ["read"]
}
```

## Caching and Refresh

- **Cache TTL** — fetched secrets are cached in Redis (default: 5 minutes) to reduce Vault load
- **Refresh** — secrets are re-fetched on each sync; use `refreshInterval` for long-running apps
- **Invalidation** — changing the Vault path in Git triggers an immediate re-fetch

## Security Considerations

- **Least privilege** — scope Vault policies to only the paths the operator needs
- **Audit** — Vault audit logs record every read; correlate with Wardn's audit log
- **No plaintext in Git** — manifests contain only Vault paths, never values
- **Encrypted transport** — always use TLS between the operator and Vault

## Vault Direct vs ESO

| Aspect | Vault Direct | ESO + Vault |
|--------|-------------|-------------|
| Extra operator | No | Yes (ESO) |
| Latency | Fetch at apply time | Continuous sync |
| Complexity | Lower | Higher |
| Features | Basic fetch | Full ESO feature set |
| Best for | Simple setups | Teams already using ESO |
