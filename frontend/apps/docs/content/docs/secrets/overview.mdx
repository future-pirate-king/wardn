# Secret Management Overview

Secrets are hard in GitOps — you can't commit plaintext secrets to Git, but Git is your source of truth. Wardn solves this with three complementary layers, all manageable from a single UI.

## The Three Layers

```
┌─────────────────────────────────────────────────────┐
│                  Git Repository                     │
│                                                     │
│  Layer 1: SOPS          Layer 2: ESO CRDs           │
│  (encrypted files)      (ExternalSecret manifests)  │
│       │                        │                    │
└───────┼────────────────────────┼────────────────────┘
        │                        │
        ▼                        ▼
┌───────────────┐      ┌───────────────────┐
│   Operator    │      │  External Secrets │
│  (decrypt at  │      │    Operator       │
│  apply time)  │      │  (syncs secrets)  │
└───────┬───────┘      └─────────┬─────────┘
        │                        │
        │      ┌─────────────────┘
        ▼      ▼
┌──────────────────────┐    ┌─────────────────────┐
│  K8s Secrets         │    │  Layer 3: Vault     │
│  (in target cluster) │◀───│  (direct integration│
└──────────────────────┘    │   optional)         │
                            └─────────────────────┘
```

| Layer | Best For | Status |
|-------|----------|--------|
| **SOPS** | Teams already encrypting files in Git | ✅ Available |
| **External Secrets Operator** | Teams with existing secret managers (AWS SM, GCP SM, Vault) | ✅ Available |
| **Vault Direct** | Teams wanting Wardn to talk to Vault directly | 📋 Planned |

## Layer 1: SOPS

[SOPS](https://github.com/getsops/sops) encrypts values in YAML/JSON files while keeping keys readable. Wardn decrypts at apply time — plaintext secrets never touch Git.

```yaml
apiVersion: v1
kind: Secret
metadata:
    name: my-secret
sops:
    kms: 'arn:aws:kms:us-east-1:...'
    encrypted_value: |
        ENC[AES256_GCM,data:...,tag:...]
```

**Best when:** You want secrets versioned in Git alongside your manifests.

## Layer 2: External Secrets Operator

[ESO](https://external-secrets.io) syncs secrets from external providers (AWS Secrets Manager, GCP Secret Manager, Vault, Azure Key Vault) into Kubernetes Secrets. Wardn watches ESO CRDs and surfaces their sync status in the UI.

```yaml
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: my-secret
spec:
  secretStoreRef:
    name: aws-secrets-manager
  target:
    name: my-secret
  data:
    - secretKey: password
      remoteRef:
        key: prod/my-app/password
```

**Best when:** Secrets live in a dedicated secret manager and you don't want them in Git at all.

## Layer 3: Vault Direct

<Callout type="info">
  Direct Vault integration is planned. It will allow Wardn to fetch secrets from Vault at apply time without ESO.
</Callout>

**Best when:** You want the simplest possible setup — Wardn talks to Vault directly, no intermediate operator.

## Unified UI

All three layers are visible in a single interface:

- **Secret Stores page** — configure and test connections to SOPS keys, ESO stores, and Vault
- **Application detail** — see which secrets an app uses and their sync status
- **Health integration** — ESO sync failures surface as app health degradation

## Choosing an Approach

| Criteria | SOPS | ESO | Vault Direct |
|----------|------|-----|--------------|
| Secrets in Git | Encrypted, yes | No (references only) | No |
| Requires extra operator | No | Yes (ESO) | No |
| Key rotation | Re-encrypt files | Provider-side | Provider-side |
| Audit trail | Git history | Provider audit logs | Vault audit logs |
| Complexity | Low | Medium | Low-Medium |

## Security Principles

1. **Never plaintext in Git** — all three layers prevent this
2. **Least privilege** — decryption keys and provider credentials are scoped per project
3. **No secrets in logs** — Wardn redacts secret values from all logs and API responses
4. **Encrypted at rest** — secret store credentials are encrypted in the database
